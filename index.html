03 / Architecture & Workflow

One content format. Separate reading and writing paths.

The public frontend fetches JSON directly. The optional Express API runs locally and reads and writes the same file in the checkout.

  3. Review & test

04 / Case Study

Make the project explain itself.

A writing and implementation exercise: turn an endpoint-first demo into a portfolio a reviewer can understand before reading the code.

01

The problem

The original page opened with API details and generic feed entries. It demonstrated mechanics, but gave a reviewer little context about the writing decisions or the work to evaluate.

02

The approach

Start with the purpose. Let readers try the experience, inspect complete writing samples, and follow the content workflow before introducing endpoint details.

03

The implementation

Reorganize the existing static site, replace placeholders with task-based documentation, and link each summary to a full sample. Keep the small content model and existing security protections.

04

The deliverables

A portfolio landing page, four complete writing samples, a searchable library with export, a workflow diagram, and a local API reference. The repository also contains setup guidance and automated browser and security checks.

Tradeoffs & next steps

Small enough to inspect.

Plain HTML, CSS, and JavaScript keep the project easy to run and compatible with GitHub Pages. A flat content file suits this small collection; it does not provide editorial roles or a publishing dashboard. Reader research and usability testing would be the next steps before claiming the structure works for a wider audience.

05 / API Reference

For a closer technical look.

This reference describes the optional local Express server at http://localhost:3001. These routes are not hosted by GitHub Pages.

Local development only Follow the secure setup instructions first. Startup requires a server-side API_TOKEN. Never put the token in the website.

GET /api/posts

Returns all posts as an array, newest date first. Query parameters on this route are ignored. No token required.

GET /api/posts/filter

tag matches exactly and is case-sensitive. q searches titles, summaries, and tags without case sensitivity. Both conditions must match; no matches returns []. Repeated query values return 400.

curl 'http://localhost:3001/api/posts/filter?tag=reference&q=filter'

POST /api/posts

Requires Authorization: Bearer <API_TOKEN> and a JSON object with title and a real YYYY-MM-DD date. Optional fields: id, summary, tags, and url. An omitted ID is generated from the date and title. Returns 201 with the complete updated array.

Limits: title 300 characters, summary 10,000, ID 320, URL 2,048; up to 20 tags of 64 characters. Only HTTP(S) or relative URLs without embedded credentials are allowed.

GET /health

Returns {"ok":true}. No token required.

Errors & request protections

Errors have the shape {"error":"message"}. Status codes: 400 invalid input or JSON; 401 unauthorized write; 404 unknown route; 409 duplicate ID; 413 body over 32 KiB; 415 unsupported encoding; 429 rate limit; 500 internal failure with details hidden.

Exact configured CORS origins, Helmet headers, and per-IP limits protect the API: 300 requests/minute and 20 writes/minute. Writes require authentication; the server binds to loopback. Those Express protections do not supply headers for the separate static site.
